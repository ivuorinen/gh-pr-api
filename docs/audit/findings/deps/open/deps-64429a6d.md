# SQLitePCLRaw.core is declared explicitly but resolves identically without it

## Problem

`src/GhPrApi/GhPrApi.csproj` declares both `SQLitePCLRaw.bundle_e_sqlite3` and
`SQLitePCLRaw.core` at 3.0.5. The `core` declaration is redundant: `bundle_e_sqlite3`
already brings `core` at exactly 3.0.5 through its own dependency chain, so removing the
explicit entry changes nothing about what is restored.

Class: redundant manifest declaration (a duplicate-dependency variant, where the duplicate
is between a direct entry and the transitive it already receives).

## Evidence

**Manifest** — `src/GhPrApi/GhPrApi.csproj:26-27`

```xml
<PackageReference Include="SQLitePCLRaw.bundle_e_sqlite3" Version="3.0.5" />
<PackageReference Include="SQLitePCLRaw.core" Version="3.0.5" />
```

**Lockfile** — `src/GhPrApi/packages.lock.json` currently records both as `Direct`.

**Usage scan** — neither package is referenced from source. Both are declared purely to pin
a transitive version:

```text
$ grep -rn --include='*.cs' -E 'SQLitePCL|Batteries_V2' src/ tests/
(no matches)
```

That is a legitimate reference form for NuGet, so neither is an unused-dependency. The
question is only whether the `core` entry does any work.

**Proof that it does not.** Removing the `core` line and re-running
`dotnet restore --force-evaluate` resolves the family identically:

```text
SQLitePCLRaw.bundle_e_sqlite3: 3.0.5  (Direct)
SQLitePCLRaw.config.e_sqlite3: 3.0.5  (Transitive)
SQLitePCLRaw.core:             3.0.5  (Transitive)
SQLitePCLRaw.provider.e_sqlite3: 3.0.5 (Transitive)
```

`core` still lands on 3.0.5 via bundle -> config -> provider -> core. The declaration was
reverted after the check; the working tree is unchanged.

## Impact

Low, and partly defensible. The cost is a manifest entry that implies a constraint it is not
providing, plus one extra package Dependabot will open independent bump PRs for. Against
that, an explicit floor does guard against a future `bundle_e_sqlite3` release lowering its
transitive floor on `core` — and this repository has already been bitten once by a
transitive (GHSA-2m69-gcr7-jv3q), which is why the pins exist at all.

So this is a judgement call, not a defect: keep it as deliberate belt-and-braces, or drop it
as noise.

## Fix

Removal is behaviour-affecting in principle and is not applied automatically. If the entry
should go, delete `src/GhPrApi/GhPrApi.csproj:27`:

```xml
<PackageReference Include="SQLitePCLRaw.core" Version="3.0.5" />
```

then run `dotnet restore src/GhPrApi/GhPrApi.csproj --force-evaluate` and commit the
regenerated `packages.lock.json`.

If it should stay, extend the existing comment above the block to say the `core` entry is a
deliberate floor guard rather than a required pin, so the next reader does not have to
re-derive that it is redundant today.
